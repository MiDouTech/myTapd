# 工单“预计结束时间”与超时时长需求分析

## 1. 结论

客户需求合理，但不建议再新增一个与现有字段同义的数据库字段。

系统现有的 `ticket.expected_time`（前端名为 `expectedTime`）已能承载“预计结束时间”：

- 新建工单时可选择“期望完成时间”；
- 工单列表和详情接口均已返回 `expectedTime`；
- 缺陷工单详情已展示“预计结束”，且有权用户可修改；
- 公开工单页已展示该时间。

因此，**字段能力已基本满足，不需要增表字段**。当前未完全满足的是：

1. 工单列表虽有 `expectedTime` 数据，但未展示该列；
2. 现有能力只能显示“已逾期”或“SLA 已超时”，不会显示具体超时时长；
3. 普通工单的登录态详情页尚未统一展示“预计结束”。

建议将需求改写为：**复用现有“期望完成时间”，在工单列表及详情统一显示为“预计结束时间”；超过该时间后，展示已超时的自然时长。**

## 2. 现有功能盘点

| 能力 | 现状 | 是否满足 |
| --- | --- | --- |
| 保存预计结束时间 | `ticket.expected_time` 已存在，可为空 | 满足 |
| 创建时填写 | 新建页已有“期望完成时间” | 满足 |
| 详情展示 | 缺陷详情和公开页已展示，其他内部详情展示不统一 | 部分满足 |
| 修改预计时间 | 缺陷详情支持有权用户编辑 | 部分满足 |
| 列表展示 | API 已返回，表格未显示 | 不满足 |
| 超时判定 | 缺陷摘要有 `isOverdue`；SLA 有 `BREACHED` | 部分满足 |
| 超时多久 | 无通用返回字段，前端仅显示“已逾期/已超时” | 不满足 |

## 3. “预计结束时间”的定义

结合现有字段命名、数据库注释和交互方式，本需求中的“预计结束时间”应定义为：

> **对外展示的工单预计完成时间：优先使用人工填写的客户期望/双方约定时间，未填写时默认使用 SLA 解决截止时间。**

它复用现有的 `expectedTime`。数据库中的 `expected_time` 仍只保存人工承诺时间；查询结果在该值为空时回退到 `RESOLVE` 计时器的 `deadline`，不将默认值反写到工单表。

不应采用“创建时间 + 响应时间 + 解决时间”的原因是：

1. 现有 SLA 在工单创建时同时启动“响应”和“解决”两个计时器，解决时限并不是等响应计时结束后才开始；
2. 因此直接相加会重复计时，得到比 SLA 实际解决截止时间更晚的错误结果；
3. SLA 还需要考虑工作时间、节假日、挂起与恢复，不能用普通日历加法代替；
4. 客户约定的交付时间可能来自项目计划或人工评估，未必等于 SLA 上限。

如果产品还希望展示一个由系统自动计算的时间，应另行命名为 **“SLA 解决截止时间”**，并直接使用 `RESOLVE` 计时器的 `deadline`，而不要填入或覆盖 `expectedTime`。

### 3.1 与 SLA 的边界

“预计结束时间”与 SLA 截止时间不应混为同一概念：

- **预计结束时间**：客户期望或工单相关人与客户约定的最终交付时间，适合对客户展示，按自然时间计算；
- **SLA deadline**：系统按分类绑定的 SLA 策略、工作时间和暂停/恢复规则自动计算，分为响应和解决计时器。

现有 SLA 已具备截止时间、预警、超时标记及通知能力，并在工单列表显示“正常 / 预警中 / 已超时”。但 SLA 不能替代客户指定的预计结束时间，而且当前对已超时计时器只返回零剩余时长，不返回超时时长。

## 4. 建议的产品口径

### 4.1 字段命名

页面统一显示为“预计结束时间”，技术上继续使用 `expectedTime` / `expected_time`。不新增 `estimated_end_time` 等重复字段，避免两个时间不一致。

### 4.2 超时计算规则

1. `expectedTime` 为空：显示 `-`，不判定超时；
2. 未完成工单：`max(当前时间 - expectedTime, 0)`；
3. 已完成/已关闭工单：`max(实际结束时间 - expectedTime, 0)`，超时时长在结束后固定，不再继续增长；
4. 实际结束时间优先取 `resolvedAt`，无解决时间时取 `closedAt`；
5. 该时长按自然时间计算，不扣除非工作时段。若客户要求“工作时长超时”，应明确改为 SLA 超时时长需求。

### 4.3 展示规则

- 未超时：显示“预计结束 2026-07-30 18:00”；
- 超时不足 1 分钟：显示“已超时 < 1分钟”；
- 不足 24 小时：显示“已超时 3小时25分钟”；
- 达到 24 小时：显示“已超时 2天3小时”；
- 列表可红色高亮，详情同时展示完整时间和超时时长。

## 5. 建议实施范围

### 第一期（建议）

1. 复用 `expectedTime`，统一页面文案；
2. 在工单列表增加“预计结束时间”列；
3. 在所有内部详情页展示该字段；
4. 按上述口径展示动态/固定的超时时长；
5. 保留现有 SLA 列，两者分开展示。

### 第二期（可选）

- 增加预计结束时间范围筛选和逾期筛选；
- 增加按预计结束时间排序；
- 对即将逾期的工单增加提醒；
- 若要求追溯预计时间的变更，将每次修改记入字段变更日志。

## 6. 验收标准

- 创建或编辑工单后，列表和详情显示同一个预计结束时间；
- 未到期、进行中超时、按时完成、超时完成四种情况的文案和时长均正确；
- 完成或关闭后的超时时长不再增长；
- 无 `expectedTime` 的工单不误判为超时；
- SLA 状态与人工预计结束时间逾期状态各自独立，互不覆盖。

## 7. 待客户确认

1. 客户口中的“预计结束”是否确认指客户期望/双方约定的完成时间？若客户实际指 SLA 时限，页面应改称“SLA 解决截止时间”。
2. 时长按自然时间还是工作时间计算？
3. 完成时间取“已解决”还是“已关闭”节点？
4. 哪些角色可修改预计结束时间，修改是否必须填写原因？
5. 是否需要列表筛选、排序和到期前提醒？
